# Changelog

Changes to the `UVision.Hosting` and `UVision.Client` NuGet packages. Versions 0.2.0 and 0.2.1 were never published; their changes ship in 0.3.0.

## [Unreleased]

### Added
- Counting scenarios (`type: counting`): the engine counts the objects in a photo and compares the count with an expected value. A scenario carries `expected_count` (required), `count_tolerance` (default 0), `min_confidence` (0 exclusive to 1; empty means `UVision:Detection:MinConfidence`, default 0.5) and `count_classes` (the detector labels to count; empty counts every detected kind); all four are nullable and are refused on other scenario types, so existing scenario files and responses are unchanged. The decision classes stay `OK` / `NG` (inside / outside `expected_count ± count_tolerance`) and the single tier is `detector`; the VLM never counts. The result and the stored record carry a nullable `count` object (`total`, `by_class`, `expected`, `tolerance`, `min_confidence`, `uncertain`, `boxes` as ratios of the original photo, `model_sha256` when the server reports it); the v1 response stays the OK/NG view with a one-line finding. A box close to the threshold (within 0.1) that could change the outcome makes the result `NG` with `requires_review: true` and `posture: "review_block"`
- `UVision:Detection` (`DETECTION_PROVIDER`, `DETECTION_ENDPOINT`, `DETECTION_MODEL`, `DETECTION_TOKEN` for the standalone server): the object detector behind counting. `none` (the default) means no detector: counting scenarios are refused with 503 (`detection_unavailable`, nothing recorded) because a count that is not known is never reported as `OK`; other scenarios are unaffected. `mock` is a deterministic demo that does not look at the photo. `mloop` reads the boxes of an object-detection model served by `mloop serve` (0.46.0 or later; a startup log line says so when the server is older). The response shape of a real detection model has not been checked against a live server yet
- Counting scenarios are kept out of classification training: `POST /datasets/export` and `GET /datasets/readiness` answer 409 for them, and the oracle second opinion skips them, because their `OK` / `NG` says the count is inside the tolerance, not that the photo is defective
- The console creates and edits counting scenarios (expected count, tolerance, minimum confidence, counted kinds) and the result detail draws the counted boxes over the photo, with boxes near the threshold outlined differently
- The benchmark tool has `count-error --input counts.json`: it scores a detector's boxes against the true counts per photo for a list of confidence thresholds — exact-match rate, within-one rate, signed error, 95th percentile and maximum error, the share that would go to a person for confirmation — and splits the result by true count (0, 1-5, 6-20, 21+). It does not call a detector; the boxes come from the input file
- The console's offline queue no longer hammers the server with a capture it keeps refusing (a deterministic 5xx): the periodic retry of such a capture now waits 15 s, 30 s, 60 s … up to 10 minutes between attempts, a connection-restored signal still retries at once, and from the fifth consecutive refusal the camera view says that the server keeps refusing N captures. The line stays unblocked and the capture stays on the device.
- Retention: `POST /scenarios/{id}/retention/purge` (admin PIN) lets an installer delete accumulated records by date range and kind. The engine still never deletes anything by itself. The request names `from` / `to` (the current UTC day and later are refused) and `kinds` (`records` = a day's photos, results, labels and anomaly maps; `ledger`; `metrics`; anything not named is kept). `dry_run` defaults to true and returns what would go — file count and bytes per kind, and what would be lost (results, human labels, labels in no dataset export, open questions about the removed photos, ledger decisions, metric rows) plus `covered_by_export`. A real delete needs `dry_run: false` and the `plan_fingerprint` of that plan (a hash of the range's file list and sizes): if the range changed since, or the fingerprint belongs to another range or kind, it is refused with 409. Open questions about removed photos are withdrawn. Each purge appends a line to `retention.jsonl` in the scenario folder, which is never deleted. `UVision.Client` and the console's wire types carry the new types.
- `UVision:Storage:DatasetExportKeep` (default 0 = keep everything) keeps only the newest N dataset exports of a scenario after a new one is created. An export can be rebuilt from the labels, so this is safe to automate; the export just created and any export a registered model version points to are always kept. It never touches results, ledger or metrics.
- The metrics summary reports the blind audit by class side, because one overall consistency rate hides disagreements on a rare class: `audit_ng_ng`, `audit_ng_ok`, `audit_ok_ng`, `audit_ok_ok` (a label's first blind re-label against the label in force before it, split by defect side) and `audit_positive_agreement` / `audit_negative_agreement` (the positive and negative specific agreement, `2a/(2a+b+c)` and `2d/(2d+b+c)`; `null` while there is no such pair). Re-audits after a conflict was resolved and learning-stream labels are not counted. The console's metrics tab shows both rates under the consistency card.
- The metrics summary reports the false-alarm side next to NG recall, from human OK labels only (learning-stream labels stay out, as for recall): `labeled_ok`, `vlm_false_alarms`, `vlm_false_alarm_rate` (verdict NG on a photo a person labeled OK) and `ml_ok_scored`, `ml_false_alarms`, `ml_false_alarm_rate` (the dedicated model's NG on the same photos; a degraded or absent model is left out of its denominator). The rates are `null` while there is no denominator. `label_consistency_rate`'s description now says what it measures: how often a blind re-label agrees with the first label (repeatability), not accuracy against the truth. `UVision.Client` and the console's wire types carry the new fields. The console's metrics tab shows the false-alarm rate in a card beside NG recall (lower is better), so a model that calls more photos defective is not read as better on recall alone.
- The dataset export manifest records each item's label `stream` (`learn` for labels gathered by actively choosing which photos to ask about) and leaves the field out for labels without a marker, so a trainer that holds out an evaluation share can keep the `learn` items out of it. `UVision.Client` and the console's wire types carry the new field.
- The operator screen has a "photo check" button (not shown for part-verification scenarios) that opens a card over the camera, which stays alive underneath: one photo at a time with a large button per class and "don't know". It shows no reason for why the photo was picked, locks the buttons while an answer is sent, and moves on to the next question when the server says the question was already closed. An empty queue and a failed load each have a retry.
- A question queue: `GET /questions/next` hands a device one photo at a time to classify and `POST /questions/answer` takes the answer, either a class (written as a label marked `stream: "learn"`) or an abstention (`abstain: true`, "don't know"; recorded as its own history event, never as a label, so training, the export and the metrics do not read it). A photo is asked once, a photo that already has a label is not asked, a device that has not answered yet is shown the same question again, and an answer is refused with 409 when the photo was labelled elsewhere in the meantime (the label is not overwritten). Each question is stored as `{scenario}/questions/{question_id}.json` with the reason it was asked, so the labels it produced can be told apart later. Both endpoints need no PIN, like the other operator endpoints. `UVision:Questions:Rule` picks the photo: `uncertain` (default) or `random`. `uncertain` asks the photo the strongest running judge was least sure of, taken from what it left in the decision ledger, with `RandomFloor` (default 0.25) of the picks still random: when the patch scores were recorded, the photo whose patch score is closest to the pass mark (the 95th percentile of the patch scores of photos answered as normal in a representative pick, at least 10 of them; answers collected by `uncertain` picks are left out because they gather hard normal cases and would push the pass mark up); otherwise the photo the case memory was least sure of. With no signal yet (memory off, or too few representative normal answers) it starts at random and never falls back to the case memory's own uncertainty, which ranked worse than random against a patch-score judge; `WindowDays` (default 7) limits how far back photos are considered. Verification scenarios are not supported (400). Picking the next photo reads one ledger file per window day, the earlier questions from an in-memory index (built once per process from the question files, loaded in parallel, and kept current by the store's own writes) and, for the picked photo only, its label sidecar — it does not list every label or reopen every earlier question, which on a network share took tens of seconds per request once a few hundred photos had been asked. `UVision.Client` and the console's wire types carry the new endpoints.
- Label history events can carry a `stream` marker (`measure` or `learn`). A label written without it reads as `measure`, exactly as before, and an event without the marker serializes byte for byte like an older sidecar. Labels marked `learn` are the ones gathered by actively choosing which photos to ask about, so hard cases are over-represented: they feed the case memory and the training export as usual, but the daily metrics (NG recall, the promotion-eligibility signal, label consistency and the oracle comparison) and the blind-audit sample read only `measure` labels. `UVision.Client` and the console's wire types carry the new field.
- `GET /health` reports the free space of the volume that holds the data root: `data_volume` with `free_bytes` (what this process can write, quota included), `total_bytes` and `low`, which turns true when the free space falls below `UVision:Storage:LowSpaceWarningBytes` (default 2 GiB; 0 or less disables the flag and leaves the numbers). The field is left out where the volume cannot be measured (a UNC path, a drive that is not ready), and the endpoint never fails because of it. A full disk makes the inspection record fail to save, so the signal lets the installer notice beforehand; the engine itself never deletes or refuses anything because of it. `UVision.Client` and the console's wire types carry the new field.
- The console's metrics tab shows the data volume's free space (read from `GET /health`) and turns red with a warning when the server reports it as low; nothing is drawn when the server cannot measure the volume.
- The question queue can plant questions with a known answer: `UVision:Questions:PlantRate` (default 0 = none, behaviour unchanged). With a rate above 0 each question is, with that probability, a reference image whose answer is known instead of a regular question, shown on the same card; the solver's answer is recorded as a hit or a miss in a per-scenario plant record (`plants/plants.jsonl`) and in a recheck pool (`pool/`, "don't know" counts as reached and as neither hit nor miss), never as a label, so a planted answer does not reach training or judgement. The response's `reason` is masked as a regular question's, a device is not shown the same reference twice until every reference was shown once, and a reference whose answer the solver cannot choose (an undeclared defect type) is not planted.
- `GET /questions/solver-trust?scenario_id=` reports how each solver (device) did on the planted questions: planted, correct, wrong, unsure ("don't know"), still open, and an accuracy that is only given once at least 10 questions were answered (an accuracy from a handful of answers would read as trust); "don't know" and unanswered questions never count against the accuracy. The console's metrics tab shows it as a card per scenario, and draws nothing while no question was planted.
- `GET /questions/image?scenario_id=&question_id=` serves a question's photo from one address shape for every question, so the address does not reveal where the photo came from (a reference image's own address carries its answer). The console's question card uses it instead of the results image route, which still works unchanged.
- The console has a "retention" tab for the purge endpoint: pick a scenario, a date range (up to yesterday, UTC) and the kinds to delete, ask for the plan first (nothing is deleted), read what would be lost — files and bytes per kind, records, human labels not yet in any dataset export, open questions that would be withdrawn, ledger decisions, metric rows, and an export advice when labels are not covered — then tick the irreversibility confirmation and delete. The screen sends the plan's fingerprint back, drops a plan as soon as any input changes, and asks for a new plan when the server answers 409. The admin PIN is asked once, like every other console change.
- `GET /results` accepts `limit` (1 to 1000) and `cursor`: with `limit` the list is read newest first, only that many records are opened, and when more exist the response header `X-Next-Cursor` carries the `cursor` for the next call. Without `limit` nothing changes (every record of the day, same body and order). Reading a day's list opens one file per record, which is cheap on a local disk but takes seconds to tens of seconds for a few thousand records on a network share; a page reads only its own records. New inspections arriving between two pages neither shift nor repeat the rest.
- Scenarios can choose the encoder of their own patch memory: the optional `patch_encoder` field (an encoder id registered in MLoop, including intermediate-layer and concatenated-layer encoders; empty means the configured `UVision:Memory:Encoder`). Which layer separates normal from defective differs by target — a middle layer on circuit boards, the last layer on solid objects — so the layer is picked per scenario by replaying its own ledger. Only the patch scores use it: the case memory (the global vectors, its distance scale and the `MaxDistance` threshold) stays on the installation's encoder, because an intermediate layer's global vector sits in a very different distance scale (measured about 1/40 of the last layer) that one installation-wide threshold cannot fit. A scenario that sets it costs one more embedding per inspection (run in parallel), its patch memory is built in the chosen encoder's space (the version key carries the encoder), an id that is not a plain identifier (letters, digits, `.`, `_`, `-`, up to 64) is rejected with 400, and an id MLoop does not know only drops the patch scores (the case-memory answer is unaffected). The ledger gets `memory:patch_encoder` when the patch scores come from a different encoder than the case memory. Omitting the field on `PUT` keeps the stored value; an empty string clears it. Scenarios that do not set it are unchanged byte for byte. `IImageEmbedder.EmbedPatchesAsync` takes an optional encoder id.
- `UVision:Memory:PatchBankPatches` (default 0 = off, as before): an upper bound on the number of patches the patch memory scores against. When it is positive and the collected normal patches exceed it, the memory is reduced with a greedy k-center selection that keeps the patches covering the edge of normal appearance, so a tenth of the patches keeps the score of the full memory almost unchanged while the per-inspection computation shrinks by the same ratio. The selection runs once while the memory snapshot is built (in the background sync, never on the inspection path) and again only when the set of normal cases changes; the ledger gets `memory:bank_patches` when the memory was reduced. It never affects the verdict, and the global score still uses every normal case.
- `UVision:Vlm:TimeoutSeconds` (`VLM_TIMEOUT_SECONDS` for the standalone server): a time limit for the vision model call of one inspection, 0 (the default, no limit — as before) or 1 to 600, checked at startup. A reasoning model can think for minutes on some images and the provider SDK retries failed requests, so without a limit an operator waits until the model server or a gateway gives up. Past the limit the inspection is unavailable (503 `vlm_unavailable`), the same as a vision model failure; the limit covers the SDK's retries.
- `UVision:Vlm:MaxOutputTokens` (`VLM_MAX_OUTPUT_TOKENS`): the model's output token limit for one inspection, 4096 by default as before, 256 to 131072, checked at startup. A reasoning model spends tokens thinking before it writes the JSON answer, and on a hard image it can use the whole limit and stop with no answer; raise it for such a model, within the server's context length.
- `UVision:Vlm:ThinkingEffort` (`VLM_THINKING_EFFORT`): the reasoning effort sent with each inspection to a reasoning model — `none`, `minimal`, `low`, `medium`, `high` or `xhigh`; left empty (the default) nothing is sent, as before. An unknown value stops startup. It changes verdict quality as well as latency, so measure it on the scenario's own samples before turning it on; a server that does not take it ignores it.
- The benchmark tool's vision model run reads a sample list (`--manifest <name>`, `--split`, `--per-class N` spread evenly across each class), runs calls concurrently (`--concurrency N`), and records a failed call as a failed row — left out of the accuracy, counted in the report, exit code 3 — instead of stopping. The per-image table includes the model's findings.
- The benchmark tool measures the dedicated ML classifier with the split kept: `classify --export <folder>` copies a sample list's `train` split into an MLoop image-classification folder (`<folder>/<class>/`, files named by content hash), and `classify --endpoint <mloop serve>` sends its `test` split through the same `mloop` classifier the server uses and reports the confusion table, the defect recall and how many defects passed as OK (`--per-class N`, `--max-per-minute N` to stay under `mloop serve`'s request limit). `manifest --split-csv <csv> [--object <name>]` builds a sample list from a split file shipped with a dataset (columns `split`, `label`, `image`, optional `object`) instead of split folders.
- The benchmark tool's vision model run can take its few-shot reference images from a sample list's `train` split (`--refs-manifest <name>`, `--refs-cap N` per class), so the references never overlap the `test` images being judged. The report no longer carries the static price table, which listed list prices of models it does not measure.
- The benchmark tool turns COCO box annotations into per-part crops: `crops --name <name> --coco-dir <dirs> --image-dir <dirs> --split train|test --classes <box name>=<class>,…` cuts each mapped box (padded by `--pad`, default 0.1, dropped below `--min-side`, default 24 px) out of its image into `GEN/u-vision/crops/<name>/<class>/` under the data root and writes a sample list, so a dataset that photographs many parts per image can be judged part by part. `--append` merges a second split into the same list with the usual duplicate and leak removal.
- The benchmark tool's few-shot reference images can be shifted (`--refs-offset N`): same spacing across the `train` split, a different set of images, to see how much a result depends on which references were picked.
- The benchmark tool builds a comparison table from its own reports: `summary --dir <report folders>` reads the vision model and ML classifier reports and prints one row each — defects caught out of all defects (a call that could not decide counts as a miss), false alarms on good samples, and undecided calls — so the table is never copied by hand.
- The console's reference image panel tells you when an inspection scenario has no reference images: a judging model without references calls good parts defective more often (false alarms). It is only a notice — saving and judging work as before — and verification scenarios, which compare against an expected part number, never show it.
- The benchmark tool's `summary` also prints a judge-by-scenario table (one row per sample list, one column per judge, each cell the defects caught and the false alarms; repeated runs in a cell are joined with ` ; `). The vision model report now names its sample list in the header (`- 목록: `<name>``); older reports are matched by their file name (`<date>-<list>-<judge>…`).
- The benchmark tool's `summary --sources <ledger.tsv>` adds a coverage table: per sample list, its data source and terms of use (from a hand-written tab-separated ledger of prefix, data, terms), then each judge's defects caught, false alarms, undecided calls and median latency. A list the ledger does not cover is shown as terms unconfirmed rather than left blank. The report summary also reads each report's median latency.
- The benchmark tool scores images by patch features: `patches --manifest <name> [--bank N]` (MLoop 0.46.0 or later) puts patch embeddings of some `train` normal images in a memory bank, takes the worst patch's nearest cosine distance as an image's anomaly score, and compares it with the whole-image vector score at the same normal false-alarm rate (defects missed at 1 / 5 / 10 %, AUROC). Embeddings are cached per encoder version.
- `IImageEmbedder` gains an optional patch mode: `SupportsPatches` and `EmbedPatchesAsync` (up to 8 images per call, the global vector plus the patch vectors of one MLoop `/embed?patches=true` run), as default interface members, so existing implementations keep working. The `mloop` embedder implements it; `mock` returns deterministic hash patches. `EncoderIdentity` carries the encoder's preprocessing version (`Preprocessor`, MLoop 0.46.0+) without changing the memory's version key. The patch score computation moves from the benchmark tool into `PatchDistance`, so the replay tool and the server compute the same score. Nothing in the server's behaviour changes.
- `classify --export` takes `--per-class N` to export at most N training images per class, spread evenly, for sample lists too large to train on in reasonable time; the benchmark tool's reports are now written as UTF-8 whatever the console's code page.
- `inject` takes `--per-class N` (with `--offset K` for a different, equally spaced set): it picks N samples per class spread over the whole list and feeds them in an order that mixes the classes in proportion. Cutting the list at its start with `--limit` alone took neighbouring images of whichever class the sorted list begins with.
- The benchmark tool replays the anomaly scores a scenario's decision ledger has accumulated: `ledger-replay --data <engine data folder> --scenario <id>` joins the ledger's whole-image and patch scores with the people's labels and compares them — AUROC and defects missed at the same normal false-alarm rate — by the size of the normal memory at decision time. Read only.
- The benchmark tool measures repeat consistency: `repeat --a <report> --b <report>` pairs two runs of the same vision-model setup over the same samples and splits the judge's errors into noise (the answer moves when asked again) and systematic error (the same wrong answer twice), plus how often the defect call flipped, using the same computation as HoneAI's repeat consistency.
- The console's result detail shows a heat-map button when the inspection has an anomaly map: it lays the patch grid over the captured image, colouring the patches farthest from the normal memory (the colour is relative to that image; the absolute patch and whole-image scores are shown beside it). Without a map the screen is unchanged.
- `GET /results/anomaly-map?scenario_id=&date=&image_id=` returns an inspection's anomaly map when `UVision:Memory:Patches` is on: for each patch of the image, the cosine distance to the nearest patch of the normal memory (rows, columns, the covered crop in image pixels, the distances row by row, and the two scores), so a review screen can show where the image differs from the normal cases. Observation only. `PatchDistance.PatchMap` is the per-patch distances the patch score takes the maximum of. `UVision.Client` and the OpenAPI document gain the endpoint.
- `UVision:Memory:Patches` (off by default) and `UVision:Memory:PatchBankCap` (default 200, 1 to 5000): the confirmed-case memory can also keep the patch vectors of the most recent normal cases and, for every inspection, record two anomaly scores against that same normal memory in the decision ledger (`memory:global_score`, `memory:patch_score`, `memory:bank_size`) — the nearest whole-image distance and the worst patch's nearest patch distance. Observation only: verdicts, responses and records do not change. The query then uses the embedder's patch mode (about 1 MB per call with `mloop`) and the score takes some CPU; it needs a provider with a patch mode (`mock`, `mloop` 0.46.0 or later). With 256 patches of 384 dimensions, 200 normal images take about 79 MB per scenario. Patch files of cases that fall out of the memory are deleted on the next sync.
- The confirmed-case memory's version key now includes the encoder's preprocessing version when the encoder reports one (MLoop 0.46.0 or later). The same weights with changed preprocessing produce different vectors, so they are a different space; memories built earlier are rebuilt once under the new key from the stored images.
- The decision ledger's vision model tier now records the teacher edition, not just the model name: `{provider}:{model}|p:<8 hex>|r:<8 hex>`, where `p` hashes the system prompt (criteria, defect classes) and the settings that change the answer (image downscale, output token limit, reasoning effort) and `r` hashes the reference images' content, order and labels (`none` without any). The same model with different references or criteria is a different edition. Ledger lines written before this have no suffix. The request and response formats are unchanged.
- The benchmark tool's `patches` can compare against an MLoop `image-anomaly` model (MLoop 0.47.0 or later): `--bank-out <folder>` copies the memory bank's images to a folder to train that model on the same pictures, and `--anomaly-endpoint <url>` scores the same queries through its `POST /predict` and adds a row (AUROC, defects missed at fixed false-alarm rates, per-image latency). `--subsample 0.5,0.25,0.1` re-scores the same queries on a randomly reduced bank (seeded) to show what a cheaper search would cost in accuracy.
- The benchmark tool measures what a model server leaves behind after an embedding answer: `embed-cpu --manifest <name> --server-pid <pid>` calls `/embed` (with or without patches), reads the server process's CPU time right after the answer, 0.4 s and 1.5 s later, and times the same patch distance computation right after the answer and after the server has rested — so a server that keeps burning cores after replying shows up as a slower computation on the same machine.
- `CoresetSelector` (hosting library, pure): greedy k-center selection of memory patches — keeps the patches that cover what the memory showed instead of a random share, so a reduced patch bank still contains the rare normal textures a random share would drop. Distances are measured on a seeded 128-dimension random projection; the same input and seed give the same selection. The benchmark tool's `patches --coreset 0.5,0.25,0.1` scores the same queries on a bank reduced this way next to the random reduction; nothing in the engine uses it yet.
- The benchmark tool times the result list read at scale (and, with `--page`, the paged read): `results-scale --counts 500,1000,2000,5000` writes that many synthetic results through the real store into one day folder and times listing them (first read, repeated reads, response serialization and size); `--dir` points it at any folder, for example a network share.
- The benchmark tool measures whether a model can grade an image on an ordered scale (for example top > middle > low): `grade --manifest <name> --order <best,…,worst> --endpoint <OpenAI-compatible /v1> --model <id>` shows a few reference images per grade from the `train` split (`--refs-per-class`, 0 for zero-shot), asks about the `test` split one image at a time, and reports exact accuracy, accuracy within one step, the confusion table, per-grade recall and the failure reasons. The temperature is only sent when `--temperature` is given — some providers reject it. The report also shows what guessing without looking would score — a uniformly random guess and the best single fixed grade — because within one step is near-free when there are only three grades; `--criteria <file>` appends a written definition of the grades to the prompt.
- The benchmark tool's `inject` takes `--label-after` (plant the ground-truth labels once the whole batch is posted, so a query batch carries its truth for `ledger-replay` without each query seeing the earlier ones as memory) and prints the request latency (p50, p95, max) of the batch. `classify` takes `--out <path>` like the other measurement commands.
- A memory query logs, at Debug level, where its time went: embedding, decision and patch score (`UVision.Api.Services.Memory.CaseMemory`).

### Changed
- The per-day label list (read by the case-memory sync, the metrics summary, the automatic demotion check and the dataset export) is served from an in-memory index instead of reopening every label sidecar on each call. The index is built once per day folder (sidecars read in parallel), is kept current by the label store's own writes (label, abstention, oracle opinion, audit, delete) and is dropped when the day folder disappears; it is derived data, rebuilt from the files at the next start. A label sidecar edited by hand outside the engine is only seen after a restart, as before for a single-process store. On a network share each sidecar cost roughly 10 to 20 ms, so a few hundred labels in a day made every one of those calls take seconds.
- The dataset export warns about a class with too few samples by the scenario's `trust.training.min_per_class` (default 30), the same threshold the training readiness report (`build_ready`) uses; before, the export warned at a fixed 5, so a class with 5 to 29 samples got no warning while readiness said it was not ready. The warning text now names that setting.
- `promotion_eligible` (the promotion-readiness signal in the metrics summary) is no longer decided from a handful of labeled defects: it now also needs `labeled_ng` and `ml_ng_scored` to reach the new `UVision:Authority:MinNgSamples` (default 59, about the number of defects that lets zero misses support a recall of 0.95 at 95 % confidence). Below that the field is omitted, as it already was below `MinWindow`; before, one human-labeled defect that the ML classifier caught and the vision model missed was enough for `true`. The signal is still a point estimate and is documented as a transitional signal. Promotion itself remains a manual, PIN-protected decision.
- When the vision model stops at the output token limit, the inspection's failure now says so (the limit and the setting to raise) instead of reporting an empty or malformed answer.
- The benchmark tool's reports no longer keep web addresses that appear in a failed call's message (they are replaced by `<url>`).
- Upgraded `HoneAI.Core` to 0.15.0 (adds an "unsure" answer kind to the recheck pool that counts as reached without being a label or a failure; no code change was needed here and the full test suite passes unchanged).
- Upgraded `HoneAI.Core` to 0.14.0 (0.13.0 added patch embeddings and the encoder's preprocessing version to the MLoop client; 0.14.0 only reorders a parameter of the model lifecycle interface, which the server does not use). Nothing in the server's behaviour changes; the requests MLoop receives are the same.
- The patch search runs in cache-sized tiles: several query patches share each slice of the memory bank instead of each re-reading all of it. Every pairwise dot product and the maximum are unchanged, so the distances are byte-identical; about twice as fast with 600 images in the bank.

### Fixed
- The console's offline capture queue no longer drops a capture when the server answers but cannot record it. A capture whose request ended in a 500 (the inspection result could not be saved, for example a full disk or a briefly unavailable share) or a 502 / 503 / 504 (a proxy in front of an engine that is restarting) stays in the queue and is sent again when the connection or the server recovers; the same capture id is the idempotency key, so a resend never judges it twice. A capture the server rejected (400, 404, 413, 415) or declared undecidable (503 `detection_unavailable`, fail-closed) is still removed. A capture left in the queue does not hold back the ones behind it.
- The console's result detail wraps long values (image id, expected part, read code) instead of making the dialog scroll sideways on a narrow screen.

## [0.5.0] - 2026-10-24

### Changed
- **Breaking: the `mloop` ML classifier sends the image itself and needs MLoop 0.45.0 or later.** `POST /predict` now receives the image contents as base64 (`{"images": [...]}`) instead of a row holding a path to a temporary file, so `mloop serve` no longer has to run on the same machine as U-Vision. `UVision:Ml:ImageColumn` (`ML_IMAGE_COLUMN`) is removed — MLoop picks the image column of an image-classification model itself. The classifier now takes the confidence MLoop reports for the prediction and no longer derives one from the class probabilities when it is missing; a prediction without a finite confidence counts as confidence 0. Migration: upgrade `mloop serve` to 0.45.0 or later and drop `ImageColumn` from configuration.
- The confirmed-case memory needs MLoop 0.45.0 or later as well: 0.44.0 decoded images with an alpha channel (translucent PNGs) differently, and the encoder version it reports is the same in both, so the memory cannot tell the two apart.
- When the ML classifier or the memory uses `mloop`, the server reads `GET /health` from each MLoop endpoint once after startup and logs its version; an older version than 0.45.0 is a warning naming what will fail and how to upgrade. An unreachable MLoop is logged as information, since it may start after U-Vision. Startup and verdicts are not affected.
- Calls to MLoop time out: `UVision:Ml:TimeoutSeconds` (default 15) and `UVision:Memory:TimeoutSeconds` (default 30, which also covers the memory sync's batches of 64), each 1 to 600, checked at startup. Before, a stalled MLoop held every inspection for up to 100 seconds, since the response waits for the ML answer; now the inspection goes on without it (ML) or the memory abstains. The memory sync and the oracle sweep treat a timeout like any other failed round and try again on the next one; only shutdown ends them.
- Upgraded `HoneAI.Core` to 0.12.0. The `mloop` ML classifier and the confirmed-case memory now call MLoop through HoneAI's MLoop client (`IMLoopClient.PredictImagesAsync` and `EmbedAsync`) instead of their own HTTP code; the requests MLoop receives, the timeouts and the confidence rule are unchanged. `MloopClassifier` and `MloopImageEmbedder` take an `IMLoopClient` instead of an `HttpClient` — code that builds them directly passes `MloopClient.Create(endpoint, timeoutSeconds, token)`; the factories are unchanged. The admin console footer uses `@uplatform/brand` 0.4.1, whose U-Vision link now points to the product site instead of the source repository.
- The OpenAPI contract describes optional properties as the server writes them: a property left out when it is null or default is optional and never null, and in schemas that only appear in responses every other property is required (it is always written, even when its C# type has a default). Requests and responses are unchanged; `UVision.Client` is unaffected apart from a doc comment. The admin console's TypeScript wire types are now generated from this contract (`npm run generate:types` in `client/`, checked in CI) instead of mirrored by hand.
- The OpenAPI contract (`server/openapi/u-vision.json`, `/openapi/v1.json`) describes numbers as numbers. It used to type every number as "a number or a numeric string" with a pattern, which is how the server is lenient when reading, not what it writes; a client generated from the contract no longer sees a string alternative. Requests and responses are unchanged, and `UVision.Client` is unaffected (its generator had already dropped the string form).

### Added
- `POST /v2/inspect` accepts an optional capture origin: `origin=dataset` with an optional `origin_ref` (letters, digits, `. _ : -`, up to 128) marks an inspection fed from a test dataset rather than captured on site. It is judged and recorded as usual — it goes into training, the memory and the gate — and the origin is kept in the v2 result (and so in the inspection event), the stored result (`origin`, `origin_ref`), the metrics row (`origin`) and the decision ledger (`origin:kind`, `origin:ref`). `GET /metrics` reports `dataset_inspections`, and the console's metrics view says when injected inspections are mixed into the figures. Without an origin nothing changes. Any other `origin`, or `origin_ref` alone, is a 400. `/inspect` (v1) does not take it.
- Confirmed-case memory, a judge below the ML classifier and the vision model that answers from images people have labelled. It embeds each capture with a pretrained image encoder served by MLoop (`POST /embed`, MLoop 0.45.0 or later — the image contents are sent, so MLoop need not share a disk with U-Vision) and answers a class only when the `Neighbors` nearest labelled cases (default 5) all share it and the nearest is within `MaxDistance` cosine distance (default 0.15); otherwise it abstains. It only observes for now: its answer and distances are recorded in the decision ledger (`memory:*` annotations) and its step appears in the v2 `path`, while the verdict, the `/inspect` response and stored results are unchanged. It applies to inspection scenarios only — a verification's match or mismatch depends on the expected part, not on the image alone.
- Configured under `UVision:Memory` (`MEMORY_*` for the standalone server): `Provider` (`none` by default, `mock`, `mloop`), `Endpoint`, `Encoder` (the id of an encoder installed in MLoop — U-Vision ships no weights), `Token`, `Neighbors`, `MaxDistance` and `SyncIntervalSeconds`. An unknown provider or a missing endpoint or encoder stops startup. A background sync embeds newly labelled images in batches of 64 and caches the vectors under `{DataPath}/{scenario}/memory/{encoder}/vectors.jsonl`, one directory per encoder version; the cache can be deleted and is rebuilt. Label changes reach the memory on the next sync. A scenario's `judges` accept the new `memory` tier.
- `GET {ApiBasePath}/memory?scenario_id=&date=`: the memory's state (encoder version, number of cases, when it was last built) and a threshold replay of that day's ledger — for each cosine distance, how many inspections the memory would have answered, how often that matched the verdict actually returned and the people's labels, and how many it would have passed as OK that people labelled defective — both as a share of the answered inspections (`miss_rate`) and of all labelled defects (`defect_pass_rate`, out of `labeled_defects`), since the first stays small when defects are rare even if several of them pass. The threshold ladder is 0.01, 0.02, 0.03, 0.05, 0.10, 0.15, 0.20 and 0.30 plus the configured value; nearest-neighbour distances between real photos are mostly below 0.06. The ledger now also records the class the neighbours agreed on when the nearest case was beyond the threshold (`memory:agreed_class`), so a wider threshold can be replayed. Read-only, no PIN. `UVision.Client` gains the call.
- The benchmark tool (`server/src/UVision.Benchmark`) measures the confirmed-case memory offline, without a vision model: `manifest` writes a sample list (path, split, class) for a folder of labelled images under a data root (`UVISION_DATA_ROOT`) into `GEN/u-vision/manifests/` — files with the same content count once and test files that also appear in train are dropped, so a duplicated or leaked image cannot look like a correct answer — and `memory` puts the `train` split into the memory, queries the `test` split through MLoop `/embed` and replays thresholds with the same rules the server uses, reporting the nearest-distance spread per class and, per threshold, how many queries the memory would answer, how often correctly, and how many of the queried defects it would pass as OK. Vectors are cached per encoder version next to the sample list. `inject` feeds a sample list to a running engine through `UVision.Client` (`POST /v2/inspect` with `origin=dataset` and `origin_ref=<list>:<content hash>`) and, with `--label`, records each sample's class as the person's label (by `dataset:<list>`), so the dataset goes through training, the memory and the gate like site captures; it prints how the verdicts compare with the classes. The blind audit sample (`GET /results/audit-sample`) leaves out these dataset labels — a label whose `by` starts with `dataset:` — since the audit measures how consistent people's labels are. `MemoryReplay.Run` takes an optional list of thresholds.
- The admin console's metrics view shows the memory when it is on: its state and the replay table, with the configured threshold highlighted and thresholds that would have passed a defect as OK marked.

### Fixed
- The admin console's reference gallery showed no reference images: it sorted them by `label` as `"ok"` and `"ng"`, while the server sends `0` (ok) and `1` (ng). The console now reads the numbers; the wire is unchanged. The OpenAPI contract describes `ReferenceLabel` with those two values.

### Changed

Versions up to and including 0.3.0 stay under MIT. Contributions require signing the CLA (`CLA.md`).

- **Breaking: the self-hosted vision provider is `openai-compatible`.** It replaces `gpustack` and the reserved `vllm` value, for the vision model (`UVision:Vlm:Provider`, `VLM_PROVIDER`) and the oracle (`UVision:Oracle:Provider`). It talks to any server with the OpenAI API — GPUStack, vLLM, Ollama or a gateway in front of them — at the server address in `Endpoint`, adding the standard `/v1` path unless the address already ends with it; the API key is optional. Migration: change `gpustack` to `openai-compatible` and keep the same endpoint. Requests to a GPUStack server are unchanged.
- An unknown or unbuilt provider value, or `openai-compatible` without an `Endpoint`, now stops startup with a message listing the accepted values, instead of failing on the first inspection (or, for the oracle's `openai` / `google`, with a not-implemented error). The oracle accepts `none` and `openai-compatible` only.
- `IScenarioStore.CreateAsync` returns `Scenario?`: `null` when the requested `scenario_id` is already in use. A custom store implements the same contract.
- Upgraded IronHive to 0.69.0. IronHive no longer brings in MessagePack, SQLite (`Microsoft.Data.Sqlite`, `SQLitePCLRaw`), PdfPig, DocumentFormat.OpenXml or HtmlAgilityPack, so `UVision.Hosting` no longer carries them transitively; U-Vision used none of them.

### Added
- `UVision.Client`, a new package: a typed HTTP client for the engine server, generated with Kiota from the OpenAPI contract (`server/openapi/u-vision.json`). `UVisionClient.Create(httpClient, baseAddress, apiBasePath)` takes the address the engine is reached at (including any proxy prefix) and its API base path (default `/api/u-vision`); routes are relative to that base, so an engine under another base path needs no rewriting. Multipart uploads (`inspect`, `v2/inspect`, reference images) are sent as Kiota `MultipartBody` with the contract's field names as part names; documented error responses arrive as `ProblemDetails` or `DetectionUnavailableResponse` exceptions. Licensed MIT, unlike the engine: the client links into the calling application, on the other side of the process boundary. Depends on `Microsoft.Kiota.Bundle` 2.1.2.
- `server/Dockerfile`: a container image of the engine server (PWA and API in one process). It publishes for the image's platform only, runs as the image's non-root user, listens on 8080 and keeps all server data under the `/data` volume. CI builds the image on every push and publishes it to `ghcr.io/iyulab/u-vision` for each release tag, tagged `X.Y.Z` and `X.Y` (and `latest` for the newest release), for linux/amd64 and linux/arm64. Install by version tag. The SDK stage runs on the build machine and cross-publishes for the target platform.
- `samples/ClientIntegration`: another application calling the engine server with `UVision.Client` — listing scenarios, sending an image to `/v2/inspect` (with an expected part for part verification) and handling the result, review hold, `503` and rejections. It replaces `samples/MinimalHost`, which showed the in-process mount and pinned `UVision.Hosting` 0.1.0 with its vulnerable image library. CI builds the samples against the packages of the same commit.
- `samples/SameOriginMount`: a reverse proxy in front of the engine server that serves the U-Vision screens and API under a host application's own origin, passing `/u-vision/` and `/api/u-vision/` through unchanged.
- The admin console footer shows the U-Platform affiliation element (`@uplatform/brand` 0.4.0): one line linking to the U-Platform family, with the other products in a drop-down. It makes no network requests and sets no cookies.
- Decision ledger. Every inspection appends one line to `{DataPath}/{scenario}/ledger/{yyyy-MM-dd}.jsonl`: a HoneAI `PredictionProvenance` from a tiered router over the answers the inspection already received (ML below, VLM on top), with the verdict actually returned recorded beside it (`operative:*` annotations). The router only observes: with no trust policy yet, every slice is in shadow, so the VLM settles and responses are unchanged. A ledger write failure is logged and does not affect the inspection. Adds a dependency on `HoneAI.Core` 0.10.0, which has no further dependencies.
- Scenario definition v2 fields, all optional: `type`, `trigger`, `classes` (each with `settleable` / `must_catch`), `judges` (tier order, top last) and `trust` (`slice_key`, `targets`). A scenario without them reads as today's OK/NG inspection, and they are omitted from `scenario.json` and responses when unset, so existing scenarios are unchanged byte for byte. The decision ledger now takes its settlement policy, slice key and tier order from the scenario. Only values that are built are accepted (`type: inspection`, `trigger: still`, tiers `ml` and `vlm` with `vlm` on top, `slice_key: scenario-v1`); anything else is rejected with `400`. Updating a scenario without v2 fields keeps the stored ones.
- `POST {ApiBasePath}/v2/inspect`: the same request, decision and records as `/inspect`, answered in a v2 shape — `class` (a scenario class id), `settled_by` (the tier that decided), `confidence`, `findings` (when the VLM decided), `requires_review` (when two judges ran) and `path`, the router's per-tier outcome (`settled`, `shadowed`, `escalated`, `abstained`). When no decision can be made it returns `503` with `detection_unavailable`, `reason` and `path`. The `/inspect` response is unchanged.
- Part verification scenarios (`type: verification`, classes `MATCH` / `MISMATCH`). `/v2/inspect` takes `expected_part` and, when the capturing device decoded one, `observed_code`. A deterministic match tier compares the two below the vision model (it answers `MATCH`/`MISMATCH`, or abstains without a code); the vision model is told the expected part and its OK/NG answer is read as `MATCH`/`MISMATCH`. A verification scenario requires `expected_part`, so it cannot be called through `/inspect`. Stored results gain `expected_part` and `observed_code` when they were sent. The dedicated ML classifier is called only when the scenario's tiers include it.
- The operator screen supports part verification scenarios: an "expected part" field appears for them, captures go to `/v2/inspect` with the code read by the browser's `BarcodeDetector` when one is available, and the result shows as match / mismatch. The admin console can set a scenario's type. Changing a scenario's type drops its stored classes and tiers instead of carrying them over.
- Results views (results table, detail, today's list, label audit) read OK/NG as match / mismatch for verification scenarios, and the detail shows the expected part and the code read. Stored values stay OK/NG.
- Part verification reads codes in browsers without a built-in `BarcodeDetector` (iOS Safari, most desktop browsers) through a ZXing WebAssembly implementation of the same API (`barcode-detector` 3.2.3). It is loaded only when the built-in one is missing, and its `.wasm` file ships with the app and is served from the same origin, so no CDN is contacted and it works offline once cached.
- Every endpoint now carries OpenAPI metadata: an `operationId`, the response type for each status, and the problem responses it can return (upload validation `400`/`413`/`415`, admin PIN `401`/`503`). A host that calls `AddOpenApi()` gets a complete description of the U-Vision API under the `U-Vision` tag; the package itself does not depend on an OpenAPI generator. The standalone server serves the document at `/openapi/v1.json`, and the repository keeps a copy in `server/openapi/u-vision.json`.
- Offline capture queue on the operator screen. Each capture is written to the device (IndexedDB) before it is sent. When the server cannot be reached the capture stays queued, the screen says so and accepts the next item, and queued captures are sent oldest first when the browser comes back online or every 15 seconds while any are waiting. Their results appear in the recent list marked as late, with the capture time; they never replace the current result or raise the review gate. A late NG (or mismatch) instead raises a banner with its capture time that stays until the operator confirms it. Only connection failures are retried: a capture the server answered — rejected, or "unable to decide" — is not sent again. Browsers without IndexedDB send directly as before.
- `/inspect` and `/v2/inspect` accept `captured_at`, the time the device took the picture (ISO 8601 with a time zone). It is stored as `captured_at` (UTC) on the result record; `timestamp` and the date folder stay the time the server received it. A value without a time zone, or one that does not parse, is rejected with `400`.
- Decision events for other systems. Configure receivers under `UVision:Events:Webhooks` (`Name`, `Url`, optional `Secret`) and every decision is written to a per-receiver outbox under the scenario's `events/` folder, then posted by a background service, so responses never wait on a receiver. Events are CloudEvents 1.0 JSON (`type` `u-vision.inspection.decided`, `id` = the decision id) whose `data` is the `/v2/inspect` result. Requests are signed per the Standard Webhooks spec (`webhook-id`, `webhook-timestamp`, `webhook-signature`). Delivery is at least once: failures back off from 10 seconds up to an hour, and after `MaxAttempts` (15) the event moves to `dead/`. With no receivers configured nothing is written. An invalid receiver name or URL stops startup.
- Metrics are recorded for every inspection, not only when a dedicated ML classifier is enabled. A row whose decision did not ask the classifier carries `vlm_only: true` and stays out of the ML ratios; part verification rows add `match` (`MATCH`, `MISMATCH` or `abstained`) and `contested`. `GET {ApiBasePath}/metrics` adds `ml_checked` — the inspections that asked the classifier, now the denominator of the agreement, review and degrade rates and of the promotion and auto-demotion windows — and `match_mismatches`, `match_abstained` and `contested`; `inspections` counts every decided inspection. Existing rows read as before. Responses and stored results are unchanged. The metrics tab shows the code-match counts for verification scenarios.
- Creating a scenario takes an optional `scenario_id`. The id names the scenario's data folder and appears in decision events and CSV exports, and it cannot change later; without it the id is still derived from the name's ASCII letters and digits, which leaves a name in another script as `scenario` or bare digits. A given id uses the same characters as other ids (letters, digits, `.`, `_`, `-`; up to 128) or is rejected with `400`, and an id already in use is rejected with `409` rather than suffixed. An update that names a different id is rejected with `400`. The admin console has an optional id field for new scenarios and asks for one when the name has no Latin letters.
- A lower tier's must-catch answer is no longer overruled silently. When a tier below answers a value that must not be missed (in part verification, the code read from the label differs from the expected part) and the tier above settles a different class, the decision is held for review: the `/v2/inspect` result carries `requires_review: true`, `posture: "review_block"` and `contested_by` (each entry a `tier` and the `class` it answered), and the stored result carries `requires_review` and `posture` the same way. `class` stays the upper tier's answer. The operator screen blocks the next capture until the operator confirms and says that the code read differs from the expected part. The `/v2/inspect` result also carries `posture` when the authority stage raises a blocking review.
- The `/v2/inspect` result carries `device_id`, `device_label` and `captured_at` when the request sent them, so decision events say which device took the picture and when. They are omitted otherwise; the `/inspect` response is unchanged.
- `GET {ApiBasePath}/events/status` reports, per webhook receiver, how many events are waiting, how many were given up, when the oldest waiting one was created and the kind of its last failure (an HTTP status or an exception type, never the error text). The admin console shows it above the metrics when receivers are configured.
- `/inspect` and `/v2/inspect` accept an `Idempotency-Key` header (letters, digits, `.`, `_`, `-`; up to 128 characters). The first `200` response for a key is kept under the scenario's `idempotency/` folder; a request that repeats the key gets that response back byte for byte with `Idempotent-Replayed: true`, without a second decision, record, decision-ledger line or decision event. Reusing a key for a different request (another image, scenario, device, context, `captured_at` or endpoint) returns `422`; a request whose key is still being processed waits for it and gets the same response. Only `200` responses are kept, so a request that ended in `503` or `500` is decided again when resent. Kept responses are deleted after `UVision:Storage:IdempotencyRetentionHours` (default 168; checked hourly, `0` keeps them), after which the key counts as new. Requests without the header behave as before. The operator screen sends each queued capture's id as its key, so a capture whose response was lost on the way back is not recorded twice when the queue resends it.
- While captures wait in the device queue, the operator screen says so when the browser has not agreed to keep the site's storage (`navigator.storage.persist()` refused), since such a browser may clear queued captures under storage pressure or after the site goes unused.
- The results view opens with a summary of the day: inspections, OK and NG counts with the NG share, and — once people have labelled results — how many were checked and how many labels disagree with the verdict. Verification scenarios show match / mismatch.
- CSV export from the results view: the rows on screen (including the review-only filter) with their human labels, as UTF-8 with a BOM so spreadsheets open it directly. Cells that a spreadsheet would run as a formula are prefixed with `'`. Verification scenarios add the match / mismatch reading, the expected part and the code read.
- Defect types. An inspection scenario can declare its NG side as several types in `classes`: `OK` plus one or more type ids, each `must_catch`. The vision model is then asked for a `defect_class` constrained by the output schema to the declared ids, and an NG that names no declared type is not an answer (the request fails closed with `503`). `/v2/inspect` returns the type as `class` and stored results carry it as `class`; every type reads as `NG` in `/inspect`, whose response is unchanged. ML labels and human labels are read against the declared ids, agreement compares the type, and NG recall counts every type as NG. A scenario that declares no types keeps OK/NG, which is the case of a single type called `NG`. A custom `IVlmProvider` finds the declared types in `ScenarioContext.DefectClasses`.
- Classes take an optional display name, `label` (up to 32 characters; no control characters, `,` or `=`; unique within the scenario). Screens and exports show it while the id stays the key for records, labels and training folders, and the vision model is told each type as `id(name)` while still answering with the id. It is omitted when unset.
- The admin console sets a scenario's defect types as `id=name` pairs separated by commas. Results show the type's name next to NG, the day summary counts each type, label buttons offer the scenario's classes by name, and the CSV export adds `class` and `class_label` columns when records carry a type.
- An NG reference image whose description names a declared defect type (by id or display name) is introduced to the vision model as `id(name)`, the same way the type list names it, so the model can tie the example to the id it answers with. Other descriptions are passed as written. The reference upload field in the admin console suggests the scenario's declared types.
- Training data selection follows explicit rules: the human label is the ground truth, labels with an unresolved audit conflict are left out, every NG-side label and every record the judges disagreed on is kept, and OK samples are capped at a multiple of the NG side, picked by a hash of the image id so the pick is stable. Dataset exports apply the rules and record them in the manifest under `selection`.
- `GET {ApiBasePath}/datasets/readiness?scenario_id=…` reports when a classifier build is due: without an active model, whether every class has enough confirmed labels (`build_ready`); with one, how many labels were confirmed after the model's dataset (`new_labels_since_model`) and whether that passes the rebuild threshold (`rebuild_suggested`). Values that cannot be known are omitted rather than false. Thresholds come from the scenario's `trust.training` (`min_per_class`, `ok_ratio_cap`, `rebuild_min_new_labels`; defaults 30, 3, 30). Nothing here trains or calls a trainer. The metrics tab shows the signal in one line.

### Fixed
- On narrow screens the admin console tabs broke their names one character per line. They now stay on one line and scroll sideways.
- In manual capture mode the result badge sat under the shutter button, hiding the findings and confidence. The badge now sits above it.
- Identifiers (scenario, reference, model version, export ids) with a trailing newline passed validation, because the pattern was anchored with `$`, and could become directory names. They are now rejected.
- `201 Created` responses (scenario, reference image, model version, dataset export) returned a `Location` under `/api/u-vision` even when the host mounted the API at another `ApiBasePath`; the dataset export's `Location` also lacked the API base. `Location` now follows `ApiBasePath` and the request's `PathBase`.
- Concurrent writes to one image's label sidecar — a human label and an oracle opinion, or an audit — could drop an event or fail on the file rename. Writes to the same sidecar are now serialized.
- Embedded app files were served with a hand-written content-type table that sent `.wasm` as `application/octet-stream`, which prevents streaming WebAssembly compilation. Content types now come from ASP.NET Core's standard extension table; JavaScript is served as `text/javascript` (RFC 9239) instead of `application/javascript`.
- A PNG upload was sent to the vision model labeled as JPEG when server-side downscaling (`max_image_dimension`) is off. The image format sent to the model is now read from the image bytes.

### Changed
- The inspection pipeline (reference loading, model calls, verdict decision, record, metrics) moved out of the `/inspect` HTTP handler into `InspectionPipeline`, registered by `AddUVision`. Responses, stored records and metrics rows are unchanged byte for byte.
- Small responses that were anonymous objects now have named types (`HealthResponse`, `AuthorityTransitionResponse`, `AuditResponse`, `ModelRegisteredResponse`, `ModelPointerResponse`, `ModelListResponse`). The JSON is unchanged.
- `RequireAdminPin` now extends `RouteHandlerBuilder` (it was generic over any `IEndpointConventionBuilder`) so it can describe its `401`/`503` responses.
- `ImageUpload.ExtensionFor` moved to `ImageFiles.ExtensionFor` (`UVision.Api.Imaging`).
