# Changelog

Changes to the `UVision.Hosting` and `UVision.Client` NuGet packages. Versions 0.2.0 and 0.2.1 were never published; their changes ship in 0.3.0. The OPC UA server below lives in the engine host and its container image only; the `UVision.Hosting` package does not carry the OPC UA stack.

## [Unreleased]

### Added
- Scenarios of the new type `classification` sort a photo into one of two or more classes (part numbers, varieties, digits) instead of judging it good or bad. The classes carry no value judgement: no `OK` class is required, each class may have a `description` that goes into the VLM prompt, and each class chooses whether a lower tier may settle it (`settleable`) or whether it must always be confirmed by the top tier (`must_catch`); with neither set, every answer goes to the top. The result is the `class` of `POST /v2/inspect` (and the stored record); `POST /inspect` answers `400` for such a scenario because the result does not fold into OK/NG. The `verdict` stored with a classification result is the must-catch view: `NG` when the decided class is `must_catch`, otherwise `OK`, so the existing metrics and exports keep working. The same view is carried by the `verdict` of the `POST /v2/inspect` response and of the judgment event data (present for classification results only; other types omit it), so a receiver never has to guess it from the class name. The OPC UA result mapper used to read the OK/NG view of every result from the class name (only `OK` counted as good); for a classification result it now reads the carried `verdict`, so a class that is not must-catch is no longer reported as `NG`. A class the scenario does not declare is not an answer: the judgment is unavailable (`503`) and nothing is stored. The memory tier works for classification scenarios; the patch anomaly bank only forms when a class named `OK` exists. Reference images of a classification scenario go in one folder per class (`references/{class}`): `label` of the upload, delete and read routes is the class id, and `ReferenceInfo` gets a `class` field (its `label` is the OK/NG view of the class). `ScenarioClass` gets an optional `description`; the metrics summary gets an optional `classification` block (predicted classes, and a confusion matrix of human label against decided class). The question queue does not serve classification scenarios yet.
- The embedded console handles `classification` scenarios end to end. The scenario form has a type button and a class editor (id, display name, description, and the two flags per class) that shows the server's reasons before saving (fewer than two classes, a bad or repeated id or display name, a description over 400 characters, a class that is both settleable and must-catch); the id of a saved class is read-only because reference images and case memory are filed under it. The reference gallery draws one section per class and names the classes that have no image yet. The operator screen sends captures of such a scenario through `POST /v2/inspect` (a capture queued offline keeps the classes declared at capture time) and shows the decided class with the OK/NG view of the stored result: red only for a must-catch class, so a scenario without one never blocks the operator; its question-queue button is hidden. The results table, the label buttons and the daily summary show classes instead of OK/NG (the summary gets a class distribution), and the metrics tab gets a class card with the distribution of decisions, the agreement with human labels (withheld while there are no labels and marked indicative below 30) and the confusion matrix.
- `UVISION_WORKER_SOCKET_MODE` for the edge agent image: the Unix permission of the worker socket file as an octal value (default `0600`, owner only). A worker in another container that runs as a different user could not connect to a `0600` socket, and the host had no setting to change it; with `0660` and the agent's group on the worker the socket opens for that group only. A value that is not octal, that does not leave the owner able to read and write, or that is given without `UVISION_WORKER_SOCKET` stops the agent at start with exit code 2.
- `samples/EdgeNode`: a `docker compose` file that runs an engine and an edge agent with the shared volume for an inference worker, the permission step and the widened socket (`UVISION_WORKER_SOCKET_MODE=0660` plus the agent's group on the worker), with a short description of the line format a worker sends. Run end to end with a worker container as another user: its frames reached the engine as events, and a worker without the group was refused. It needs a release that has `UVISION_WORKER_SOCKET_MODE`.
- `GET /metrics` takes an optional `days` (1 to 90, default 1). With `days` of 2 or more the summary is computed over the whole window ending at `date`, and the response carries `window_days`. A single-day response is unchanged. Counting human-labelled defects over one day alone keeps the promotion-eligibility signal below its sample floor on lines where only a few defects are labelled per day.
- The embedded console's authority tab shows the evidence behind a promotion before it is confirmed: the human-labelled defects and good photos, the dedicated model's recall and false-alarm rate, and whether the eligibility signal is met, unmet or lacks samples, computed over the last 30 days. It is read-only and never blocks the promote button.

### Changed
- The embedded console's edit screen for a `monitoring` scenario shows its sources and rules read-only and lets only the name change. It used to show the inputs of a photo-judgment scenario (criteria, region, capture settings, resolution, reference images) and a switch of the scenario type; using that switch made the server drop the scenario's sources and rules. Defining a monitoring scenario is still done through the API.
- The embedded console no longer shows a server error as raw JSON: a failed request now shows the server's own explanation (the `detail` of the problem response) after the action, e.g. `Demoting the stage failed (409) …`. Its authority-stage tab tells the operator that a `monitoring` scenario has no authority ladder instead of offering buttons the server refuses.
- Storing a human label (`PUT /results/label`) or an audit of one (`POST /results/audit`) for a judgment that does not exist now answers `404` instead of `200`. A label belongs to a stored judgment: before, a mistyped `image_id`, a date without that judgment or a scenario that does not exist was acknowledged and left an orphan label file behind (even a directory for the unknown scenario). The identifiers of real judgments are only ever taken from the engine's own answers, so a client that labels what it was shown is not affected; a malformed identifier is still `400`, and a label for a result of a scenario that was deleted afterwards is still accepted while the result exists.
- A scenario of the type `monitoring` no longer accepts writes to the surfaces that only exist for scenarios that judge photos: exporting or checking the readiness of a classification dataset, uploading a reference image, registering, promoting or rolling back a model version, promoting or demoting the authority ladder, and storing a human label or an audit of one now answer `409` (the same answer a counting scenario already gets for its dataset). Before, they were accepted and left meaningless state behind (an empty dataset export, a reference image nothing reads, a ladder history entry). Reads of those surfaces still answer with an empty result, so a dashboard that walks every scenario meets no error.
- Changing the authority stage of a scenario that does not exist (`POST /scenarios/{id}/authority/promote` and `/demote`), and registering, promoting or rolling back a model version for one, now answers `404`. Before, the write succeeded and left a folder holding only that state: the scenario still read as `404`, but creating a scenario with the same id answered `409` ("already exists"). A folder left behind by an older version can be cleared with `DELETE /scenarios/{id}`.
- The promotion-eligibility signal (`promotion_eligible` in the metrics summary) now also requires the dedicated model's false-alarm rate on good photos to stay at or below `UVision:Authority:FalseAlarmCeiling` (default 0.10), measured over at least `UVision:Authority:MinOkSamples` (default 30) human-labelled good photos the model scored. Before, recall alone decided: a model that flagged every photo as defective passed. With fewer scored good photos than the minimum the signal is absent (`null`) instead of `true`.

- The recall term of the promotion-eligibility signal (`promotion_eligible`) no longer reads the recall of one operating point (the dedicated model's own `NG` decision). It reads the recall at a fixed false-alarm rate: the share of human-labelled defects the model scores above the highest score that keeps good photos' false alarms at or below `UVision:Authority:FalseAlarmCeiling` (ties count as passed). The same model's operating-point recall moved between 8/40 and 38/40 across twelve public targets, while its ranking quality did not. Each metrics row now carries the model's defect score (`ml_ng_score`, absent for rows written before this change and when the score cannot be read), and the metrics summary gets `ml_auroc`, `ml_recall_at_far`, `ml_ranked_ng` and `ml_ranked_ok` (all omitted while no row has a score). The signal needs at least `MinNgSamples` defects and `MinOkSamples` good photos that carry a score, so right after an upgrade it is absent (`null`) until enough new judgments have been labelled; it comes back by itself. The embedded console's authority tab shows the new values.

- `POST /scenarios/{id}/authority/promote` now asks for an explicit confirmation when a promotion is not backed by evidence. Raising a scenario to `co_primary` or `ml_primary` while its promotion-eligibility signal (read by the server over the last `UVision:Authority:EvidenceWindowDays` days, default 30) is not `true` (not met, or too few samples), and any promotion that skips a stage (for example `advisory` to `ml_primary`, even when the signal is met), answers `409` unless the request carries `"acknowledge_unverified": true`; the `detail` of the answer names the reason. Moving from `shadow` to `advisory` is unchanged. A promotion made with the confirmation is recorded in the stage history (`acknowledged_unverified` and `unverified_basis` on that entry; both absent for other entries). Callers that promote without evidence must add the field. The promotion itself stays a decision of the administrator: the field only records that the missing evidence was known. The embedded console asks for the confirmation in a box before it sends one, and marks such entries in the stage history.

### Fixed
- On Windows, reading a stored state file (a scenario, the authority ladder, a model registry, a label, an event outbox entry, a stored judgment or image) at the moment another request replaced it could fail with an I/O error, and reading an append-only file (metrics, the case-memory vectors, the re-judgment log, the retention row count) could make the append that came next fail with a sharing violation, because the standard read calls open a file for reading in a mode that excludes writers. Every such read now goes through one shared read path that does not exclude writers and retries for a few milliseconds while a replacement is under way. Linux and macOS did not have the problem.
- The version of the dedicated model's judging tier (`version` of an `ml` opinion in `POST /results/rejudge`, and the tier version in the decision ledger when that tier settles) is now the model file hash that `mloop serve` reports with each prediction when no registry version is bound; it used to fall back to the classifier name, so a retrained model that was never promoted (the previous one keeps answering) looked the same as a promoted one. A registry-bound version is unchanged, and a server that does not report the hash still gives the classifier name.

## [0.7.0] - 2026-11-04

### Added
- The events of monitoring scenarios are documented (`kind` and `data` of each rule event, the `config_stale` mark), and a camera that is already lost when a scenario is newly assigned or changed is announced to that scenario once, when its configuration takes effect, instead of leaving it unaware of the loss.
- A configuration the edge agent could not confirm with the engine for longer than `UVISION_MAX_CONFIG_AGE_HOURS` (default 24) is stale: the rules keep running on it, because an alarm that silently disappears is worse than one raised on an old rule, but every event they raise carries `config_stale: true` in its data so the receiver can decide how far to trust it. The agent remembers when it last confirmed the configuration (a successful poll, whether it brought a new configuration or confirmed the same one) across restarts, reports `worker.config_stale` in its status, and the Nodes tab shows a warning.
- An agent with a worker socket now reports how it sees the inference worker in its status report (`worker`: connected, time of the last message, frames received, lines dropped with the last reason, rules running, rules skipped with the reasons), the engine keeps it with the latest report, and the admin console's Nodes tab raises a flag when rules are waiting for a worker that is not connected, when rules were skipped, and when the worker's lines are being dropped. Only the fields an operator must act on rewrite the stored node file at once; the frame counter and the time of the last message do not.
- The edge agent container can now run the rules of monitoring scenarios: setting `UVISION_WORKER_SOCKET` to the path of a Unix socket file makes the agent listen there, feed the frames of an inference worker to the rule evaluator and write only the resulting events to its durable outbox, from where they travel like any other event. The rules run on the last configuration the agent holds on disk, so they keep running while the engine is unreachable; when the configuration changes, a scenario whose sources and rules are unchanged keeps its state (a raised alarm is not raised twice) and a changed scenario starts over. Rules that point at something that does not exist are skipped and named in the log, and an unusable socket path ends the process with exit code 2.
- The edge agent library can receive an inference worker: it listens on one Unix domain socket and reads newline-delimited JSON (`tracks` per frame with boxes in 0-1 frame coordinates, and `source_state`), keyed by the node-local camera alias. A line with broken JSON, an unknown version or type, a wrongly shaped value or a time without a time zone is dropped and counted rather than ending the connection, an overlong line is dropped whole, and a failing receiver loses only that message. A new connection replaces the old one (a restarted worker), and a connection that ends marks every known camera lost. The socket file is owner-only on Unix by default and a stale file left by a dead agent is replaced.
- The edge agent's rule evaluator also covers `alarm` rules and source state. An alarm is raised once its count condition (`min_count` or `max_count`) has held for `for_seconds` and cleared once the opposite state has held for `clear_seconds` (default `for_seconds`), so a flickering detection does not toggle it; with no frames there is no evaluation, so an absence alarm never rises on silence. A worker reports a camera as `ok`, `no_signal` or `degraded`; only changes become a `source_state` event, once for every scenario that watches that camera, a lost worker connection marks every known camera lost, and the next frame restores it. Frames and states are keyed by the node-local camera alias, which is what `camera_ref` names.
- The edge agent library gains its rule evaluator for the first rule kind, `count`: it is pure (the time of a frame is the only clock) and is fed the tracks of each frame. Inside a zone, or the whole frame, a change of the counted class is reported only after the count has held for `stable_frames` (default 5) or `stable_seconds`, so a one-frame flicker never becomes an event, and the first stable count is reported once as a baseline. Across a line, each crossing of the segment by the ground point of a track is reported with its direction and the running totals; a dead band of one percent of the frame around the line keeps a track that hovers on it from producing events, and a track that goes around the end of the segment is not counted. Rules that name a source, zone or line that does not exist are skipped with a reason instead of failing. `alarm` rules and source state events follow.
- Scenarios of the new type `monitoring` (trigger `stream`) describe what an edge node watches and which events it raises, instead of judging a photo. A scenario lists `sources` (a camera alias `camera_ref`, plus `zones` as polygons and `lines` as segments in 0-1 frame coordinates), `rules` and an optional `outputs` filter. The first two rule kinds are `count` (the number of a class inside a zone, reported as `count_changed` only after it has been stable for `stable_frames` or `stable_seconds`; with a `line` it counts crossings in and out) and `alarm` (a `min_count`/`max_count` condition that holds for `for_seconds` raises `alarm_raised`, and the opposite state holding for `clear_seconds` raises `alarm_cleared`). The boundary accepts only these built values and rejects contradictions with 400 (a rule pointing at a missing source, zone or line, mixed count/alarm fields, an `outputs` event a rule cannot emit). A camera is only ever named by an alias: an address, a host or a credential in `camera_ref` is rejected, and the real address is resolved on the node. `POST /inspect` and `POST /v2/inspect` answer 400 for such a scenario. On `PUT`, omitting `sources`/`rules`/`outputs` keeps the stored values and changing `type` drops them. The node configuration (`GET /edge/v1/config`) carries `trigger`, `sources`, `rules` and `outputs` for these scenarios, and the agent's configuration model reads them. The rules are not evaluated yet; this release step is the vocabulary and its validation.
- The edge agent has its own container image (`server/Dockerfile.edge-agent`, run by the new `uvision-edge-agent` host project; published to GHCR as `u-vision-edge-agent` for linux/amd64 and linux/arm64 on a release tag, like the engine image). It is configured by environment variables (`UVISION_ENGINE_URL`, `UVISION_REGISTRATION_TOKEN`, `UVISION_NODE_NAME`, `UVISION_POLL_SECONDS`, `UVISION_OUTBOX_MAX_MB`, `UVISION_STATE_DIR`, `UVISION_OUTBOX_DIR`, `UVISION_API_BASE_PATH`); wrong values stop it at start with every problem listed. It registers once with the one-time token and then keeps working from the credentials it stored, retrying registration while the engine is not reachable, and exits with distinct codes (`2` configuration, `3` the engine revoked the node, `4` the registration token was refused). It opens no port, runs as a non-root user, writes a health file after each cycle for the image's `HEALTHCHECK` (an unreachable engine is not unhealthy; a stuck loop is), and reports its version, which the image build stamps from the release tag. Cancelling the agent in the middle of a request now ends it cleanly instead of throwing.
- The admin console gets a "Nodes" tab for the edge nodes. After the administrator PIN is asked once, it lists every node with the last contact, the scenarios assigned to it, and what the agent reported about itself (queued items, dropped crops, parked items, agent version), and it calls out what needs a human: a node that has not been in contact for five minutes, parked items, dropped crops, a clock that is off, no scenario assigned, or no status report from a connected node. From the same tab the administrator issues a one-time registration token (shown once), replaces a node's scenario assignment, and revokes a node after a second confirmation. It is a read-and-manage screen; nothing in it affects judgments.
- Edge agents report their own state to the engine (`POST /edge/v1/status`, node credential): outbox depth and size, the number of crops dropped because of the disk limit, and the number of items parked after a permanent rejection, plus the agent version. The engine keeps only the latest report on the node record and does not rewrite it for an unchanged report within a minute. `GET /edge/nodes` and `GET /edge/v1/whoami` show it as the optional `status` object, so an operator can see how far behind a node is. The agent sends the report after each cycle's delivery; a failed report never delays delivery or marks the cycle offline, and an engine that does not know the route (an older version) is asked once per process and then left alone.
- `GET /results/decision?scenario_id=&date=&image_id=` shows why a stored judgment came out the way it did: which tier settled it, what every tier on the route did (settled, answered without authority, escalated, abstained), the dedicated ML tier's answer and whether it agreed, the settled tier's version, and the decision ledger's annotations (the decision actually used, memory distances and neighbours, counting evidence). It only reads the record and the ledger; no judge is called again and nothing is written. The ledger is best-effort, so when a judgment has no ledger line the response says `ledger_recorded: false` and leaves the route out instead of guessing. The console's result detail gets a collapsible "judgment evidence" section that loads only when opened. It also carries the human label in force, the oracle's latest second opinion and the re-judgments requested so far, each absent when there is none. The v1 and v2 inspect responses and the stored record are unchanged.
- `UVision.Edge.Agent`, the core of the edge agent, as a new library project in the repository (not packaged or deployed yet, no dependencies beyond the runtime): a durable file outbox (one file per event, atomic writes, restart recovery, a monotonic event `seq` that crops never consume, and a disk limit that drops the oldest crops first and never an event), an engine client that only ever connects out (register, `ETag` configuration polling, event batches, crop judgments with the item id as `Idempotency-Key`), and an agent that registers once and keeps its credentials and the last configuration on disk so it keeps working offline. It delivers in queue order at least once with exponential back-off, treats the engine's `duplicate` as delivered, parks permanently rejected items with their reason instead of retrying forever, stops without discarding anything when the engine revokes the node, and estimates the server clock offset from the polling response's `Date` header (median of recent samples, about half a second of resolution).
- Edge nodes poll their configuration with `GET /edge/v1/config`: a projection of the scenarios assigned to the node (identity, type, classes and the counting settings; nothing the edge does not use, such as the VLM prompt, reference images or the cloud-egress permission), with an `ETag` that fingerprints exactly that content, so a conditional poll gets an empty `304` until something the node needs changes. Assigned scenarios that were deleted are listed as `missing_scenarios` instead of being dropped silently. The response carries the server clock in `Date` (also on a `304`), which the agent uses to estimate the offset it reports with its events.
- Edge nodes can send the events their rules raise (`POST /edge/v1/events`, node credential): a batch of up to 500, answered item by item (`accepted`, `duplicate` or `rejected` with a code), so one bad item never blocks the rest. Duplicates are recognised by `(node_id, event_id)` with the event id a UUIDv7 made by the node, and still after a restart; the node's monotonic `seq` is used only to report holes (`missing_seq`), which a late arrival fills, so arrival order does not matter. Times are recorded twice and never rewritten: `device_time` (the node's clock), `received_at` (the server's) and the batch's `clock_offset_ms` when reported, with `corrected_time` derived separately; an offset beyond 60 seconds only marks the node `clock_skewed`. An administrator assigns scenarios to a node (`PUT /edge/nodes/{node_id}/scenarios`) and a node can only write events for those. Accepted events are appended to the node's own log and published as CloudEvents of type `u-vision.edge.event` through the existing event outbox, so webhooks and MQTT receive them with the same retry and ordering; the OPC UA destination, which carries judgment results, skips them. `GET /edge/nodes` now also shows `scenarios`, `clock_offset_ms` and `clock_skewed`.
- Edge node identity, the first piece of the edge control plane: an administrator issues a one-time registration token (`POST /edge/tokens`, admin PIN), an agent registers with it (`POST /edge/v1/register`) and receives a per-node secret, and then calls `/edge/v1/*` with `Authorization: Bearer {node_id}.{secret}` (`GET /edge/v1/whoami` checks the credential). Nodes are service identities, not user accounts, and agents only ever connect out to the engine. Tokens and secrets are high-entropy random values and only their SHA-256 hashes are stored (compared in constant time); the plain text appears in the issuing and registering responses only. A token works once, and a wrong, used or expired token gets the same 401. `GET /edge/nodes` lists the nodes (never a secret) and `DELETE /edge/nodes/{node_id}` revokes one at once, keeping its record. A node credential opens nothing outside `/edge/v1/*`. Storage is `{data}/edge/`, so `edge` is now a reserved name and cannot be a scenario id (an existing scenario of that name would have to be renamed).
- Retention purge (`POST /scenarios/{id}/retention/purge`) knows a fourth kind, `rejudge`: the re-judgment files (`{scenario}/rejudge/{date}.jsonl`) are deleted by date file like the ledger and the metrics, only when named, and the plan reports how many re-judgments would be lost in `lost.rejudges` (a new required field of the response). The console's retention tab lists it.
- `POST /results/rejudge` (admin PIN) asks a chosen judge about a stored judgment again, now, and puts the answer next to the original: `vlm` (the current edition of the VLM), `oracle` (the stronger second-opinion VLM configured under `UVision:Oracle`), `ml` or `memory`. The response lists each judge's class, confidence, findings, the edition that produced it and whether it differs from the original, plus a deterministic summary (`unanimous` / `split` / `none_answered`, the differing judges, a vote table). It never changes the stored judgment, the metrics, the decision ledger or the human-label sidecar; the answers go to their own append-only file, `{scenario}/rejudge/{date}.jsonl`. A judge that fails is reported as abstained, not as an error. Counting scenarios are refused (a detector decides them), and an oracle in the cloud needs the scenario's `allow_cloud_egress`.
- Judgment events can also be published over MQTT 5: `UVision:Events:Mqtt` lists brokers (`Name`, `Host`, `Port`, `UseTls`, `Username`, `Password`, `ClientId`, `TopicPrefix`, `QualityOfService`). The same CloudEvents envelope is sent in structured mode (`application/cloudevents+json`) to `{TopicPrefix}/{scenario_id}`, through the same per-destination outbox as webhooks, so retries with back-off, ordering, the give-up limit and `dead/` behave identically; the broker's acknowledgement is what deletes an event (QoS 1, at-least-once; QoS 2 is selectable). A broker that is down never delays a judgment. Brokers and webhooks share one name space, and a misconfigured broker stops the host at start. `GET /events/status` gains an optional `mqtt` list of the same per-destination counters (absent when no broker is configured, so existing responses are unchanged), and the console's events panel shows the brokers beside the webhooks. Adds the `MQTTnet` dependency (MIT) to `UVision.Hosting`.
- `GET /events/status` gains an optional `opcua` array (same shape as `mqtt`) while OPC UA is enabled; it is absent otherwise, so existing responses are unchanged. Because that transport has no subscriber acknowledgement, `pending` counts events the server has not accepted yet and `dead` is always 0. The embedded console lists the OPC UA destination beside webhooks and brokers.
- `IEventDestinationSource`: a host can add event destinations beyond the configured webhooks and MQTT brokers by registering sources in DI. Registered destinations get the same per-destination outbox, retry, ordering and give-up behaviour as the built-in transports, and count as "enabled" in `GET /events/status`. With no source registered nothing changes. Destination names must be unique across webhooks, brokers and sources (startup fails otherwise).
- The engine host can publish judgment results over OPC UA (off by default; `UVision:Events:OpcUa:Enabled`). It runs an OPC UA server and, for every judgment, raises an event of the type `UVisionResultReadyEventType` on the `ResultManagement` object (also visible from the Server object) and keeps the result in a bounded in-memory window (`UVision:Events:OpcUa:ResultWindow`, default 500, oldest dropped first). This follows the *shape* of the result management of OPC 40100-1 (Machine Vision, part 1): the event carries `IsPartial`, `ResultState` (always 1, completed), `InternalRecipeId` (the scenario id), `InternalConfigurationId` (the first 12 hex characters of the SHA-256 of the scenario definition with sorted keys), `JobId` and `ResultId` (both the decision id, the same id the webhook and MQTT events use) and `CreationTime`, plus the result spread over `Verdict` (`OK` / `NG`, as on the wire), `Class`, `SettledBy`, `SettledByKind`, `RequiresReview`, `Count` (counting scenarios only) and `Json` (the full v2 result, byte for byte the `data` of the CloudEvents envelope). `ResultManagement` has the methods `GetResultById`, `GetResultComponentsById` and `GetResultListFiltered` with the argument names and order of the specification, answering from the window; a result that has left the window is reported as not found (`error` = -1, application-defined). It does not claim conformance: the types live in the server's own namespace `urn:u-vision:result-management` instead of the OPC 40100-1 namespace, so a client that filters on the standard `ResultReadyEventType` node id does not match; the structured data types (`ResultDataType` and the identifier structures) are plain strings, numbers and, for `result` / `resultList`, JSON text; `processingTimes` (the output slot exists and is always empty), `ReleaseResultHandle`, the state machine, recipe and configuration management and result file transfer are not provided; `startIndex` / `maxResults` paging and `isComplete` follow the specification, ordered oldest first. The server offers signed and encrypted endpoints only (`AllowInsecure` adds an unsecured one for laboratories) with anonymous users, so access is controlled by the client certificate trust list under `{data}/opcua/pki`: a client's certificate first lands in `rejected/certs` and has to be copied to `trusted/certs`. Delivery has no subscriber acknowledgement: an event counts as delivered once the server has it, and a subscriber that missed it reads it back with the methods. Tested with the OPC Foundation client library (same stack as the server) and once end to end against an independent client implementation (an untrusted certificate is rejected, trusting it takes effect without a restart, a judgment through the HTTP API arrives as an event and is readable with `GetResultById`); not tested against commercial clients, real equipment or a MES.

### Changed
- The capture screen no longer offers scenarios of type `monitoring` (they raise events from edge nodes and cannot judge a photo); the admin console still lists them.
- Internal rename with the event transports made pluggable: the event dispatcher, delivery service, signal and status reader no longer carry "Webhook" in their names (`EventDispatcher`, `EventDeliveryService`, `EventDeliverySignal`, `EventStatusReader`); the webhook sending itself moved into `WebhookTransport`. No change to the webhook wire.
- `PUT /scenarios/{id}`: `allow_cloud_egress` is now optional on update. Leaving it out keeps the stored value (before, an update that did not send it silently turned the permission off); `true` / `false` replace it. Creating a scenario without it still means deny. A change is recorded in the scenario's tuning history (`option: allow_cloud_egress`). The console's scenario form shows the permission as a visible toggle that starts from the stored value, and the threshold "apply" no longer sends the field.
- Upgraded `HoneAI.Core` to 0.16.0 (the packages now ship their XML documentation; no code change was needed here and the full test suite passes).
- Upgraded `Microsoft.Kiota.Bundle` (the `UVision.Client` runtime dependency) from 2.1.2 to 2.1.6, and refreshed the client and site npm lock files within their declared ranges. The generated client is unchanged.

### Fixed
- Stopping the edge agent's worker socket at the moment a connection was being accepted could surface as a socket error instead of a normal stop, and a client that connected and vanished could end the accept loop. Both are now ignored by the loop, and the listen queue is large enough that a worker restarting in a loop is not refused on Linux while the previous connection is being replaced.
- The edge agent container's health marker could be read as empty or refused while the loop was rewriting it, so a health check running at that moment reported the agent as unhealthy (about one read in two hundred under a fast loop). The marker is now written to a temporary file and swapped in, and the reader retries the instant of the swap.
- Writing a stored file while another request was reading it could fail on Windows (the replacing rename is refused while the file is open), and a read could fail in the instant of the replacement. Atomic writes now retry the rename for a few hundred milliseconds at most, and the edge node store opens its files the same tolerant way; before this, a node list request could answer 500 while an agent was reporting its status.
- A misconfigured engine (an unknown `VLM_PROVIDER`, an unusable `Storage__DataPath`, clashing event destination names, a webhook secret that is not base64, ...) now stops at start with a one-line reason and exit code 2. It used to let the validation exception go unhandled, so the runtime aborted the process: a stack trace on stderr and an exit code of 139 in a container, which looked like a crash of the image rather than a wrong setting.
- The standalone host now writes its console output as UTF-8. On a machine whose console code page is not UTF-8 (English Windows uses 437, for example), the Korean text of startup configuration errors and of the event-delivery retry log was written as `?` once the output was redirected to a file or a service log, so the reason could not be read. A console that cannot be switched keeps its default encoding.

- `UVision:Memory:Patches` (off by default) and `UVision:Memory:PatchBankCap` (default 200, 1 to 5000): the confirmed-case memory can also keep the patch vectors of the most recent normal cases and, for every inspection, record two anomaly scores against that same normal memory in the decision ledger (`memory:global_score`, `memory:patch_score`, `memory:bank_size`) — the nearest whole-image distance and the worst patch's nearest patch distance. Observation only: verdicts, responses and records do not change. The query then uses the embedder's patch mode (about 1 MB per call with `mloop`) and the score takes some CPU; it needs a provider with a patch mode (`mock`, `mloop` 0.46.0 or later). With 256 patches of 384 dimensions, 200 normal images take about 79 MB per scenario. Patch files of cases that fall out of the memory are deleted on the next sync.
- The confirmed-case memory's version key now includes the encoder's preprocessing version when the encoder reports one (MLoop 0.46.0 or later). The same weights with changed preprocessing produce different vectors, so they are a different space; memories built earlier are rebuilt once under the new key from the stored images.
- The decision ledger's vision model tier now records the teacher edition, not just the model name: `{provider}:{model}|p:<8 hex>|r:<8 hex>`, where `p` hashes the system prompt (criteria, defect classes) and the settings that change the answer (image downscale, output token limit, reasoning effort) and `r` hashes the reference images' content, order and labels (`none` without any). The same model with different references or criteria is a different edition. Ledger lines written before this have no suffix. The request and response formats are unchanged.
- The benchmark tool's `patches` can compare against an MLoop `image-anomaly` model (MLoop 0.47.0 or later): `--bank-out <folder>` copies the memory bank's images to a folder to train that model on the same pictures, and `--anomaly-endpoint <url>` scores the same queries through its `POST /predict` and adds a row (AUROC, defects missed at fixed false-alarm rates, per-image latency). `--subsample 0.5,0.25,0.1` re-scores the same queries on a randomly reduced bank (seeded) to show what a cheaper search would cost in accuracy.
- The benchmark tool measures what a model server leaves behind after an embedding answer: `embed-cpu --manifest <name> --server-pid <pid>` calls `/embed` (with or without patches), reads the server process's CPU time right after the answer, 0.4 s and 1.5 s later, and times the same patch distance computation right after the answer and after the server has rested — so a server that keeps burning cores after replying shows up as a slower computation on the same machine.
- `CoresetSelector` (hosting library, pure): greedy k-center selection of memory patches — keeps the patches that cover what the memory showed instead of a random share, so a reduced patch bank still contains the rare normal textures a random share would drop. Distances are measured on a seeded 128-dimension random projection; the same input and seed give the same selection. The benchmark tool's `patches --coreset 0.5,0.25,0.1` scores the same queries on a bank reduced this way next to the random reduction; nothing in the engine uses it yet.
- The benchmark tool times the result list read at scale (and, with `--page`, the paged read): `results-scale --counts 500,1000,2000,5000` writes that many synthetic results through the real store into one day folder and times listing them (first read, repeated reads, response serialization and size); `--dir` points it at any folder, for example a network share.
- The benchmark tool measures whether a model can grade an image on an ordered scale (for example top > middle > low): `grade --manifest <name> --order <best,…,worst> --endpoint <OpenAI-compatible /v1> --model <id>` shows a few reference images per grade from the `train` split (`--refs-per-class`, 0 for zero-shot), asks about the `test` split one image at a time, and reports exact accuracy, accuracy within one step, the confusion table, per-grade recall and the failure reasons. The temperature is only sent when `--temperature` is given — some providers reject it. The report also shows what guessing without looking would score — a uniformly random guess and the best single fixed grade — because within one step is near-free when there are only three grades; `--criteria <file>` appends a written definition of the grades to the prompt.
- The benchmark tool's `inject` takes `--label-after` (plant the ground-truth labels once the whole batch is posted, so a query batch carries its truth for `ledger-replay` without each query seeing the earlier ones as memory) and prints the request latency (p50, p95, max) of the batch. `classify` takes `--out <path>` like the other measurement commands.
- A memory query logs, at Debug level, where its time went: embedding, decision and patch score (`UVision.Api.Services.Memory.CaseMemory`).

### Changed
- The per-day label list (read by the case-memory sync, the metrics summary, the automatic demotion check and the dataset export) is served from an in-memory index instead of reopening every label sidecar on each call. The index is built once per day folder (sidecars read in parallel), is kept current by the label store's own writes (label, abstention, oracle opinion, audit, delete) and is dropped when the day folder disappears; it is derived data, rebuilt from the files at the next start. A label sidecar edited by hand outside the engine is only seen after a restart, as before for a single-process store. On a network share each sidecar cost roughly 10 to 20 ms, so a few hundred labels in a day made every one of those calls take seconds.
- The dataset export warns about a class with too few samples by the scenario's `trust.training.min_per_class` (default 30), the same threshold the training readiness report (`build_ready`) uses; before, the export warned at a fixed 5, so a class with 5 to 29 samples got no warning while readiness said it was not ready. The warning text now names that setting.
- `promotion_eligible` (the promotion-readiness signal in the metrics summary) is no longer decided from a handful of labeled defects: it now also needs `labeled_ng` and `ml_ng_scored` to reach the new `UVision:Authority:MinNgSamples` (default 59, about the number of defects that lets zero misses support a recall of 0.95 at 95 % confidence). Below that the field is omitted, as it already was below `MinWindow`; before, one human-labeled defect that the ML classifier caught and the vision model missed was enough for `true`. The signal is still a point estimate and is documented as a transitional signal. Promotion itself remains a manual, PIN-protected decision.
- When the vision model stops at the output token limit, the inspection's failure now says so (the limit and the setting to raise) instead of reporting an empty or malformed answer.
- The benchmark tool's reports no longer keep web addresses that appear in a failed call's message (they are replaced by `<url>`).
- Upgraded the IronHive packages to 0.75.0 (from 0.69.0), SkiaSharp to 4.154.0, and the ASP.NET Core OpenAPI package and test hosts to 10.0.14; the client's dev tooling (`@types/node`, `fake-indexeddb`, `oxlint`) to their latest patch releases. No code change was needed; the full server and client test suites pass unchanged, and one `openai-compatible` inspection of an OK image and of an NG image against a self-hosted vision model returned the expected verdicts with structured output.
- Upgraded `HoneAI.Core` to 0.15.0 (adds an "unsure" answer kind to the recheck pool that counts as reached without being a label or a failure; no code change was needed here and the full test suite passes unchanged).
- Upgraded `HoneAI.Core` to 0.14.0 (0.13.0 added patch embeddings and the encoder's preprocessing version to the MLoop client; 0.14.0 only reorders a parameter of the model lifecycle interface, which the server does not use). Nothing in the server's behaviour changes; the requests MLoop receives are the same.
- The patch search runs in cache-sized tiles: several query patches share each slice of the memory bank instead of each re-reading all of it. Every pairwise dot product and the maximum are unchanged, so the distances are byte-identical; about twice as fast with 600 images in the bank.

### Fixed
- Editing a scenario no longer erases the NG type descriptions of its reference images (`ng_labels`): an update that omits them (or sends an empty map) keeps the stored ones, and a non-empty map replaces them. Before, saving a scenario from the console reset them.
- The append-only history files (`retention.jsonl` and the new `tuning.jsonl`) are written without a byte-order mark, so a tool that reads them line by line no longer fails on the first line.
- The console's offline capture queue no longer drops a capture when the server answers but cannot record it. A capture whose request ended in a 500 (the inspection result could not be saved, for example a full disk or a briefly unavailable share) or a 502 / 503 / 504 (a proxy in front of an engine that is restarting) stays in the queue and is sent again when the connection or the server recovers; the same capture id is the idempotency key, so a resend never judges it twice. A capture the server rejected (400, 404, 413, 415) or declared undecidable (503 `detection_unavailable`, fail-closed) is still removed. A capture left in the queue does not hold back the ones behind it.
- The console's result detail wraps long values (image id, expected part, read code) instead of making the dialog scroll sideways on a narrow screen.

### Changed
- **Breaking: the `mloop` ML classifier sends the image itself and needs MLoop 0.45.0 or later.** `POST /predict` now receives the image contents as base64 (`{"images": [...]}`) instead of a row holding a path to a temporary file, so `mloop serve` no longer has to run on the same machine as U-Vision. `UVision:Ml:ImageColumn` (`ML_IMAGE_COLUMN`) is removed — MLoop picks the image column of an image-classification model itself. - When the ML classifier or the memory uses `mloop`, the server reads `GET /health` from each MLoop endpoint once after startup and logs its version; an older version than 0.45.0 is a warning naming what will fail and how to upgrade. An unreachable MLoop is logged as information, since it may start after U-Vision. Startup and verdicts are not affected.
- Calls to MLoop time out: `UVision:Ml:TimeoutSeconds` (default 15) and `UVision:Memory:TimeoutSeconds` (default 30, which also covers the memory sync's batches of 64), each 1 to 600, checked at startup. Before, a stalled MLoop held every inspection for up to 100 seconds, since the response waits for the ML answer; now the inspection goes on without it (ML) or the memory abstains. The memory sync and the oracle sweep treat a timeout like any other failed round and try again on the next one; only shutdown ends them.
- Upgraded `HoneAI.Core` to 0.12.0. The `mloop` ML classifier and the confirmed-case memory now call MLoop through HoneAI's MLoop client (`IMLoopClient.PredictImagesAsync` and `EmbedAsync`) instead of their own HTTP code; the requests MLoop receives, the timeouts and the confidence rule are unchanged. `MloopClassifier` and `MloopImageEmbedder` take an `IMLoopClient` instead of an `HttpClient` — code that builds them directly passes `MloopClient.Create(endpoint, timeoutSeconds, token)`; the factories are unchanged. The admin console footer uses `@uplatform/brand` 0.4.1, whose U-Vision link now points to the product site instead of the source repository.
- The OpenAPI contract describes optional properties as the server writes them: a property left out when it is null or default is optional and never null, and in schemas that only appear in responses every other property is required (it is always written, even when its C# type has a default). Requests and responses are unchanged; `UVision.Client` is unaffected apart from a doc comment. The admin console's TypeScript wire types are now generated from this contract (`npm run generate:types` in `client/`, checked in CI) instead of mirrored by hand.
- The OpenAPI contract (`server/openapi/u-vision.json`, `/openapi/v1.json`) describes numbers as numbers. It used to type every number as "a number or a numeric string" with a pattern, which is how the server is lenient when reading, not what it writes; a client generated from the contract no longer sees a string alternative. Requests and responses are unchanged, and `UVision.Client` is unaffected (its generator had already dropped the string form).

### Added
- `POST /v2/inspect` accepts an optional capture origin: `origin=dataset` with an optional `origin_ref` (letters, digits, `. _ : -`, up to 128) marks an inspection fed from a test dataset rather than captured on site. It is judged and recorded as usual — it goes into training, the memory and the gate — and the origin is kept in the v2 result (and so in the inspection event), the stored result (`origin`, `origin_ref`), the metrics row (`origin`) and the decision ledger (`origin:kind`, `origin:ref`). `GET /metrics` reports `dataset_inspections`, and the console's metrics view says when injected inspections are mixed into the figures. Without an origin nothing changes. Any other `origin`, or `origin_ref` alone, is a 400. `/inspect` (v1) does not take it.
- Confirmed-case memory, a judge below the ML classifier and the vision model that answers from images people have labelled. It embeds each capture with a pretrained image encoder served by MLoop (`POST /embed`, MLoop 0.45.0 or later — the image contents are sent, so MLoop need not share a disk with U-Vision) and answers a class only when the `Neighbors` nearest labelled cases (default 5) all share it and the nearest is within `MaxDistance` cosine distance (default 0.15); otherwise it abstains. It only observes for now: its answer and distances are recorded in the decision ledger (`memory:*` annotations) and its step appears in the v2 `path`, while the verdict, the `/inspect` response and stored results are unchanged. It applies to inspection scenarios only — a verification's match or mismatch depends on the expected part, not on the image alone.
- Configured under `UVision:Memory` (`MEMORY_*` for the standalone server): `Provider` (`none` by default, `mock`, `mloop`), `Endpoint`, `Encoder` (the id of an encoder installed in MLoop — U-Vision ships no weights), `Token`, `Neighbors`, `MaxDistance` and `SyncIntervalSeconds`. An unknown provider or a missing endpoint or encoder stops startup. A background sync embeds newly labelled images in batches of 64 and caches the vectors under `{DataPath}/{scenario}/memory/{encoder}/vectors.jsonl`, one directory per encoder version; the cache can be deleted and is rebuilt. Label changes reach the memory on the next sync. A scenario's `judges` accept the new `memory` tier.
- `GET {ApiBasePath}/memory?scenario_id=&date=`: the memory's state (encoder version, number of cases, when it was last built) and a threshold replay of that day's ledger — for each cosine distance, how many inspections the memory would have answered, how often that matched the verdict actually returned and the people's labels, and how many it would have passed as OK that people labelled defective — both as a share of the answered inspections (`miss_rate`) and of all labelled defects (`defect_pass_rate`, out of `labeled_defects`), since the first stays small when defects are rare even if several of them pass. The threshold ladder is 0.01, 0.02, 0.03, 0.05, 0.10, 0.15, 0.20 and 0.30 plus the configured value; nearest-neighbour distances between real photos are mostly below 0.06. The ledger now also records the class the neighbours agreed on when the nearest case was beyond the threshold (`memory:agreed_class`), so a wider threshold can be replayed. Read-only, no PIN. `UVision.Client` gains the call.
- The benchmark tool (`server/src/UVision.Benchmark`) measures the confirmed-case memory offline, without a vision model: `manifest` writes a sample list (path, split, class) for a folder of labelled images under a data root (`UVISION_DATA_ROOT`) into `GEN/u-vision/manifests/` — files with the same content count once and test files that also appear in train are dropped, so a duplicated or leaked image cannot look like a correct answer — and `memory` puts the `train` split into the memory, queries the `test` split through MLoop `/embed` and replays thresholds with the same rules the server uses, reporting the nearest-distance spread per class and, per threshold, how many queries the memory would answer, how often correctly, and how many of the queried defects it would pass as OK. Vectors are cached per encoder version next to the sample list. `inject` feeds a sample list to a running engine through `UVision.Client` (`POST /v2/inspect` with `origin=dataset` and `origin_ref=<list>:<content hash>`) and, with `--label`, records each sample's class as the person's label (by `dataset:<list>`), so the dataset goes through training, the memory and the gate like site captures; it prints how the verdicts compare with the classes. The blind audit sample (`GET /results/audit-sample`) leaves out these dataset labels — a label whose `by` starts with `dataset:` — since the audit measures how consistent people's labels are. `MemoryReplay.Run` takes an optional list of thresholds.
- The admin console's metrics view shows the memory when it is on: its state and the replay table, with the configured threshold highlighted and thresholds that would have passed a defect as OK marked.

### Fixed
- The admin console's reference gallery showed no reference images: it sorted them by `label` as `"ok"` and `"ng"`, while the server sends `0` (ok) and `1` (ng). The console now reads the numbers; the wire is unchanged. The OpenAPI contract describes `ReferenceLabel` with those two values.

- `GET {ApiBasePath}/events/status` reports, per webhook receiver, how many events are waiting, how many were given up, when the oldest waiting one was created and the kind of its last failure (an HTTP status or an exception type, never the error text). The admin console shows it above the metrics when receivers are configured.
- `/inspect` and `/v2/inspect` accept an `Idempotency-Key` header (letters, digits, `.`, `_`, `-`; up to 128 characters). The first `200` response for a key is kept under the scenario's `idempotency/` folder; a request that repeats the key gets that response back byte for byte with `Idempotent-Replayed: true`, without a second decision, record, decision-ledger line or decision event. Reusing a key for a different request (another image, scenario, device, context, `captured_at` or endpoint) returns `422`; a request whose key is still being processed waits for it and gets the same response. Only `200` responses are kept, so a request that ended in `503` or `500` is decided again when resent. Kept responses are deleted after `UVision:Storage:IdempotencyRetentionHours` (default 168; checked hourly, `0` keeps them), after which the key counts as new. Requests without the header behave as before. The operator screen sends each queued capture's id as its key, so a capture whose response was lost on the way back is not recorded twice when the queue resends it.
- While captures wait in the device queue, the operator screen says so when the browser has not agreed to keep the site's storage (`navigator.storage.persist()` refused), since such a browser may clear queued captures under storage pressure or after the site goes unused.
- The results view opens with a summary of the day: inspections, OK and NG counts with the NG share, and — once people have labelled results — how many were checked and how many labels disagree with the verdict. Verification scenarios show match / mismatch.
- CSV export from the results view: the rows on screen (including the review-only filter) with their human labels, as UTF-8 with a BOM so spreadsheets open it directly. Cells that a spreadsheet would run as a formula are prefixed with `'`. Verification scenarios add the match / mismatch reading, the expected part and the code read.
- Defect types. An inspection scenario can declare its NG side as several types in `classes`: `OK` plus one or more type ids, each `must_catch`. The vision model is then asked for a `defect_class` constrained by the output schema to the declared ids, and an NG that names no declared type is not an answer (the request fails closed with `503`). `/v2/inspect` returns the type as `class` and stored results carry it as `class`; every type reads as `NG` in `/inspect`, whose response is unchanged. ML labels and human labels are read against the declared ids, agreement compares the type, and NG recall counts every type as NG. A scenario that declares no types keeps OK/NG, which is the case of a single type called `NG`. A custom `IVlmProvider` finds the declared types in `ScenarioContext.DefectClasses`.
- Classes take an optional display name, `label` (up to 32 characters; no control characters, `,` or `=`; unique within the scenario). Screens and exports show it while the id stays the key for records, labels and training folders, and the vision model is told each type as `id(name)` while still answering with the id. It is omitted when unset.
- The admin console sets a scenario's defect types as `id=name` pairs separated by commas. Results show the type's name next to NG, the day summary counts each type, label buttons offer the scenario's classes by name, and the CSV export adds `class` and `class_label` columns when records carry a type.
- An NG reference image whose description names a declared defect type (by id or display name) is introduced to the vision model as `id(name)`, the same way the type list names it, so the model can tie the example to the id it answers with. Other descriptions are passed as written. The reference upload field in the admin console suggests the scenario's declared types.
- Training data selection follows explicit rules: the human label is the ground truth, labels with an unresolved audit conflict are left out, every NG-side label and every record the judges disagreed on is kept, and OK samples are capped at a multiple of the NG side, picked by a hash of the image id so the pick is stable. Dataset exports apply the rules and record them in the manifest under `selection`.
- `GET {ApiBasePath}/datasets/readiness?scenario_id=…` reports when a classifier build is due: without an active model, whether every class has enough confirmed labels (`build_ready`); with one, how many labels were confirmed after the model's dataset (`new_labels_since_model`) and whether that passes the rebuild threshold (`rebuild_suggested`). Values that cannot be known are omitted rather than false. Thresholds come from the scenario's `trust.training` (`min_per_class`, `ok_ratio_cap`, `rebuild_min_new_labels`; defaults 30, 3, 30). Nothing here trains or calls a trainer. The metrics tab shows the signal in one line.

### Fixed
- On narrow screens the admin console tabs broke their names one character per line. They now stay on one line and scroll sideways.
- In manual capture mode the result badge sat under the shutter button, hiding the findings and confidence. The badge now sits above it.
- Identifiers (scenario, reference, model version, export ids) with a trailing newline passed validation, because the pattern was anchored with `$`, and could become directory names. They are now rejected.
- `201 Created` responses (scenario, reference image, model version, dataset export) returned a `Location` under `/api/u-vision` even when the host mounted the API at another `ApiBasePath`; the dataset export's `Location` also lacked the API base. `Location` now follows `ApiBasePath` and the request's `PathBase`.
- Concurrent writes to one image's label sidecar — a human label and an oracle opinion, or an audit — could drop an event or fail on the file rename. Writes to the same sidecar are now serialized.
- Embedded app files were served with a hand-written content-type table that sent `.wasm` as `application/octet-stream`, which prevents streaming WebAssembly compilation. Content types now come from ASP.NET Core's standard extension table; JavaScript is served as `text/javascript` (RFC 9239) instead of `application/javascript`.
- A PNG upload was sent to the vision model labeled as JPEG when server-side downscaling (`max_image_dimension`) is off. The image format sent to the model is now read from the image bytes.

### Changed
- The inspection pipeline (reference loading, model calls, verdict decision, record, metrics) moved out of the `/inspect` HTTP handler into `InspectionPipeline`, registered by `AddUVision`. Responses, stored records and metrics rows are unchanged byte for byte.
- Small responses that were anonymous objects now have named types (`HealthResponse`, `AuthorityTransitionResponse`, `AuditResponse`, `ModelRegisteredResponse`, `ModelPointerResponse`, `ModelListResponse`). The JSON is unchanged.
- `RequireAdminPin` now extends `RouteHandlerBuilder` (it was generic over any `IEndpointConventionBuilder`) so it can describe its `401`/`503` responses.
- `ImageUpload.ExtensionFor` moved to `ImageFiles.ExtensionFor` (`UVision.Api.Imaging`).
## [0.3.0] - 2026-10-22

### Security
- Removed `SixLabors.ImageSharp`. Version 3.1.12 carries three high-severity advisories (GHSA-j3p4-wp97-rph4, GHSA-j9gm-c75j-xc9q, GHSA-jjfr-hcj7-qf5w) and two moderate ones (GHSA-gwg2-r3hj-4w44, GHSA-wmxv-xphr-5c9g). Restores with NuGet audit no longer report NU1902/NU1903 for this package.
- Upgraded IronHive to 0.68.0, which clears the transitive MessagePack advisory GHSA-qhrr-8q5h-9q3h. The transitive Scriban and SQLitePCLRaw advisories that 0.1.x carried through IronHive 0.7.4 are also gone.

### Added
- First-run admin PIN setup. When no PIN is configured, `GET /api/u-vision/admin/status` reports `setup_required: true` and `POST /api/u-vision/admin/setup` sets the PIN with a one-time token written to the data directory (`admin-setup-token.txt`). The PIN is stored as a PBKDF2-SHA256 hash. A PIN set through configuration takes precedence and disables this path.

### Changed
- Image decoding and JPEG encoding now use SkiaSharp 4.153.1 (MIT). Server-side downscaling (`max_image_dimension`) uses a built-in separable bicubic resampler whose output matches the previous implementation within 1 level per channel on average. The re-encoded JPEG can differ slightly from earlier versions because the JPEG encoder changed.
- Native assets: Windows and macOS natives come with `SkiaSharp`; Linux natives (glibc and musl, x64 and arm64) come with `SkiaSharp.NativeAssets.Linux.NoDependencies`, which needs no fontconfig. Consumers add nothing per platform. If your app already references `SkiaSharp.NativeAssets.Linux`, `dotnet publish` reports a duplicate `libSkiaSharp.so`; keep one package and exclude the other with `ExcludeAssets="all"`.
- IronHive 0.68.0 requires `Microsoft.Extensions.*` 10.0.13 or later. A host that pins an older 10.0.x version of those packages gets NU1109 on restore; raise the pin.
- Accepted upload formats are unchanged (JPEG and PNG).
